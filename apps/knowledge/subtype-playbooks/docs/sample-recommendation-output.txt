==================== ssh-restriction: SSH brute force - จำกัดต้นทาง ====================
[recorded 5712 + org fixture (enforcement point; ยังไม่ระบุเครื่องมือตัด connection)]
[violations: []]

**คำแนะนำเพื่อยับยั้ง Incident**

1. **ตั้ง deny/rate-limit จาก 172.19.0.3 ไปยัง SSH (22/TCP) บน attack-endpoint**
   วิธีลงมือ: ตรวจก่อนว่า 172.19.0.3 ไม่ชนกับรายการ approved management access แล้วตั้ง deny หรือ rate-limit ที่ perimeter firewall FW-EDGE-1 เฉพาะ 172.19.0.3 → SSH (22/TCP) บน attack-endpoint (ไม่ใช่ global block) ตามที่จุดควบคุมนั้นรองรับ บันทึก rule เดิมก่อนแก้ แล้วตรวจจาก log ของจุดควบคุมว่า attempt จากต้นทางถูก deny/limit และ management access ยังเข้าบริการได้
   ก่อนลงมือ:
   - ตรวจว่า 172.19.0.3 เป็นฝั่งผู้โจมตีที่เข้ามาที่ SSH (22/TCP) บน attack-endpoint (ไม่ใช่ agent/observer และไม่อยู่ใน approved management access)
   - บันทึกค่า rule/limit ปัจจุบันของ SSH (22/TCP) บน perimeter firewall FW-EDGE-1 ก่อนแก้
   *ผลกระทบ: จำกัด 172.19.0.3 บนบริการนี้เท่านั้น; ผู้ใช้ที่ใช้ address เดียวกัน (เช่น NAT ร่วม) อาจถูกจำกัดบริการนี้ด้วย*
   *ตรวจผล: เห็น attempts จาก source ถูก deny/limit ที่จุดบังคับ และ management access ยังใช้ได้*
   ย้อนกลับ: คืนค่า rule/limit เดิมที่บันทึกไว้ก่อนแก้

**ข้อมูลที่ต้องตรวจเพิ่ม**
- เครื่องมือที่ใช้ "ตัด session/connection ที่ค้างของ 172.19.0.3 บน SSH (22/TCP)" (การตัด session/connection ที่ค้างอยู่) ยังไม่ได้ระบุว่ารองรับ และต้องทราบตัวระบุ session/connection ตามเครื่องมือนั้น จึงยังไม่แสดงเป็นขั้นตอนพร้อมลงมือ

**หมายเหตุเรื่องเครื่องมือ**
องค์กรยังไม่ได้ระบุเครื่องมือ/คำสั่ง/เมนูที่ใช้ลงมือในระบบ ข้อความข้างต้นจึงระบุเฉพาะขอบเขต เงื่อนไข และผลที่ต้องตรวจ — IR ใช้เครื่องมือขององค์กรให้ตรงตามนั้น

==================== hijack-basic: Scheduled Task Hijack - หลักฐานเบื้องต้น ====================
[synthetic Sysmon + analyst assertion]
[violations: []]

**คำแนะนำเพื่อยับยั้ง Incident**

1. **Disable \Maintenance\SyncReport (Scheduled Task) บน WKS-FIN-07**
   วิธีลงมือ: ใช้เครื่องมือจัดการ task/service ของเครื่อง WKS-FIN-07 สั่ง disable เฉพาะ \Maintenance\SyncReport (ไม่ลบรายการ และไม่ปิด scheduler/service manager ทั้งเครื่อง) แล้วตรวจสถานะว่าเป็น disabled
   ก่อนลงมือ:
   - ตรวจว่า \Maintenance\SyncReport (Scheduled Task) บน WKS-FIN-07 เป็น artifact ที่ผูกกับ payload execution ตาม evidence และการแก้ไม่อยู่ใน change record ที่อนุมัติ — ไม่แตะ artifact อื่น
   - บันทึก configuration ปัจจุบันของ \Maintenance\SyncReport (definition, actions, trigger, run-as account, ACL) ก่อนแก้
   *ผลกระทบ: งานตามรอบของ artifact นี้ไม่ทำงาน*
   *ตรวจผล: สถานะ artifact เป็น disabled และรอบ trigger ถัดไปไม่ทำงาน*
   ย้อนกลับ: คืนค่าเดิมที่บันทึกด้วยมือก่อนแก้ (ยังไม่ระบุเครื่องมือเก็บ snapshot ในระบบ)

2. **หยุด instance ของ \Maintenance\SyncReport ที่กำลังรันอยู่**
   วิธีลงมือ: ตรวจสถานะของ \Maintenance\SyncReport ก่อน ถ้ายังเป็น running ให้ใช้เครื่องมือจัดการ task/service หยุดเฉพาะ instance นั้น (การ disable ไม่หยุด instance ที่ทำงานอยู่แล้ว)
   *ตรวจผล: สถานะ artifact ไม่เป็น running*

3. **ยุติ payload process (ตัวระบุ Process: GUID {7f3a21aa-0001-6700-0000-001000000200}) บน WKS-FIN-07**
   วิธีลงมือ: ตรวจก่อนว่า process ตามตัวระบุข้างต้นยังรันอยู่ ถ้ายังรันจึงยุติเฉพาะ process นั้นด้วยตัวระบุ Process (ไม่ใช้ PID อย่างเดียว) ถ้าการหยุด instance ในขั้นก่อนหน้ายุติ payload ไปแล้วให้บันทึกผลการตรวจและไม่ยุติซ้ำ
   *ตรวจผล: ไม่พบ Process ตามตัวระบุข้างต้นใน process list*

**ตรวจผลรวมหลังดำเนินการ**
- ตรวจหลังรอบ trigger ถัดไปว่า \Maintenance\SyncReport ไม่ relaunch payload และไม่มี process ใหม่จาก artifact นี้

**ข้อมูลที่ต้องตรวจเพิ่ม**
- ไฟล์/object ที่จะ quarantine (เครื่อง + ตำแหน่ง/ตัวระบุ object): ต้องระบุ เครื่องที่เกี่ยวข้อง, ตำแหน่งไฟล์/object

**หมายเหตุเรื่องเครื่องมือ**
องค์กรยังไม่ได้ระบุเครื่องมือ/คำสั่ง/เมนูที่ใช้ลงมือในระบบ ข้อความข้างต้นจึงระบุเฉพาะขอบเขต เงื่อนไข และผลที่ต้องตรวจ — IR ใช้เครื่องมือขององค์กรให้ตรงตามนั้น
