VIGIX — Flowchart 4 ระยะ: Alert → Recommendation (แบ่ง Agent)

แต่ละบล็อกระบุ Input / Output จากโค้ดจริง และเลือก Test Case (TC-01…TC-10) ด้านล่างเพื่อดูว่าเข้าระบบแล้วได้ Recommendation อย่างไร
🤖 AI Agent (LangGraph / LLM)⚙️ ระบบอัตโนมัติ (ไม่ใช่ AI)👤 คน (SOC / IR)
ระยะ 1

Detection & Ingestion

ผู้ทำงาน: Wazuh + Backend (อัตโนมัติ)

1.1 Wazuh Detection

Wazuh Manager/Agent (ไม่ใช่ AI)
IN log เหตุการณ์จาก agent (auth, process, web, network)
OUT Alert: rule.id, rule.level, rule.mitre, srcip/user/hash/url

1.2 Webhook Ingest

Backend service (อัตโนมัติ)
IN Wazuh alert JSON
OUT Alert ใน DB + severity เบื้องต้น mapSeverity() (low…critical)

1.3 IOC Extraction

Backend service · IocRole
IN ฟิลด์ใน alert (IP, user, URL, domain, hash, file, command)
OUT IOC + networkRole (source/destination)
ข้อมูลจาก Wazuh: alert, rule, level, log, IOC ดิบ, MITRE ใน rule (rule.mitre.id ใช้เป็นหลัก) · ยังไม่มีผลจาก AI/CTI ในระยะนี้
▼Alert + IOC
ระยะ 2

AI Analysis & Triage

ผู้ทำงาน: AI Orchestrator → SOC Analyst

2.1 ThreatIntel (CTI)

🤖 Agent: ThreatIntelAgent
IN IOC จากระยะ 1
OUT reputation (VT / AbuseIPDB / MISP / OTX)

2.2 MITRE + RAG

🤖 Agents: MitreAgent → RagAgent
IN alert (rule.mitre.id จาก Wazuh) + IOC
OUT technique ATT&CK + mitreSource: WAZUH (ใช้ ID จาก Wazuh ที่ผ่านการตรวจกับ catalog) / AI_INFERRED (เดาจากข้อความเมื่อ Wazuh ไม่มี) / NONE · และ playbook/SOP จาก RAG

2.3 Risk · LLM Analyst · Classification

🤖 Agents: LlmAnalystAgent (LLM) → ClassificationAgent → ValidationAgent
IN ผล 2.1–2.2
OUT category, สรุปเหตุการณ์, validation (VALID/WARNING/INVALID)

2.4 Decision + SOC Triage

🤖 RecommendationAgent → DecisionAgent (Policy) · 👤 SOC Analyst
IN ผลวิเคราะห์ AI
OUT Incident (DISMISS / ยกเป็น Incident) + severity ที่ analyst ยืนยัน, IOC actionable
ข้อมูลจาก AI/CTI: reputation, classification, summary, risk · SOC ตรวจและยืนยัน severity/IOC ก่อนไประยะ 3
▼Incident + IOC + MITRE + AI analysis
ระยะ 3

Recommendation Generation & Validation

ผู้ทำงาน: Backend (deterministic) + LLM + Validator

3.1 Playbook Selector

Backend deterministic (ไม่ใช้ LLM)
IN MITRE technique ของ Incident
OUT Incident Playbook (เช่น PB-SSH-BRUTEFORCE) + allowedActions

3.2 Context Builder

Backend deterministic (ไม่ใช้ LLM)
IN Incident, IOC+role, MITRE, evidence, Action Catalog, Runbook, Policy, Containment Procedure (YAML)
OUT RecommendationContext (เฉพาะ Action ที่ evidence รองรับ)

3.3 LLM Agent

🤖 Agent: LlmRecommendationAgent (LLM, มี Fallback agent)
IN prompt จาก context
OUT แผน JSON: ขั้น CHECK / ACTION / MANUAL + target + evidence

3.4 Recommendation Validator

Backend deterministic (กฎ ไม่ใช้ LLM)
IN แผนจาก LLM
OUT VALIDATED หรือ INVALID_AI_OUTPUT (action นอก allowed, target ไม่อยู่ใน evidence, role ผิด → ส่งแก้ 1 ครั้ง)
AI เสนอได้เฉพาะสิ่งที่ Playbook อนุญาตและมี evidence รองรับ · CHECK/MANUAL ไม่ใช่ Action ที่สั่งรันได้
▼Recommendation (VALIDATED)
ระยะ 4

Approval, Response & Verification

ผู้ทำงาน: Policy (อัตโนมัติ) + IR Team (คน) + n8n แจ้งเตือน

4.1 Policy Check

Policy Engine (กฎ)
IN ขั้น ACTION + impact + severity
OUT ต้องอนุมัติหรือไม่ (POL-A01: impact HIGH → IR_TEAM อนุมัติ)

4.2 IR Decision & Execute

👤 IR Team (คนตัดสินใจและทำเอง)
IN Recommendation + ผลอนุมัติ
OUT Response Ticket / ผลดำเนินการ (IR ตัดสินใจและทำเอง)

4.3 Notify (n8n)

n8n automation (แจ้งอย่างเดียว)
IN เหตุการณ์ incident/approval
OUT แจ้ง Teams / queue (แจ้งอย่างเดียว ไม่สั่งรัน)

4.4 Verify (Re-hunt)

Wazuh re-hunt + 👤 IR ยืนยันผล
IN verification.yaml (re-hunt query)
OUT Resolved / Not Resolved → วนกลับ containment
