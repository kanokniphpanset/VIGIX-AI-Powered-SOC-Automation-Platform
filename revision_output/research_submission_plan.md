### B2. ระบบเปรียบเทียบและการถอดองค์ประกอบ (ทำแบบ offline ได้)

ใช้หลักฐานชุดเดิมที่ตรึงไว้ (evidence snapshot ของ v3.3) และเรียก LLM ด้วยข้อมูลนำเข้าเดียวกันทุกเงื่อนไข ไม่ต้องสร้างการโจมตีใหม่

| เงื่อนไข | องค์ประกอบ | สิ่งที่แสดง |
|---|---|---|
| C0 | LLM อย่างเดียว (ไม่มี RAG ไม่มีตัวตรวจ) | ฐานล่าง |
| C1 | LLM + RAG | ผลของการค้นคืนความรู้ |
| C2 | LLM + RAG + ตัวตรวจ (VIGIX) | ผลของตัวตรวจ |
| C3 | C2 แต่ปิดการแก้ไขอัตโนมัติ 1 ครั้ง | ผลของกลไกแก้ไข |

วัดทุกเงื่อนไขด้วย Correct Recommendation, RAC, UAR, จำนวนคำแนะนำที่ละเมิดกฎ (ใช้ตัวตรวจในโหมดบันทึกอย่างเดียวสำหรับ C0–C1) และจำนวนคำแนะนำที่เหมาะสมแต่ถูกปฏิเสธ (ต้องมีผู้เชี่ยวชาญตัดสิน) ใน repo มีผล RAG on/off บางส่วนอยู่แล้ว (`results/extended-evaluation/`) แต่ทำกับรุ่นโค้ดและคำตอบอ้างอิงก่อน v3.3 จึงใช้เป็นข้อมูลนำร่องได้เท่านั้น

### B3. คำตอบอ้างอิงและการแยกชุดข้อมูล

1. ให้ผู้เชี่ยวชาญ SOC/IR อย่างน้อย 2 คนที่ไม่ได้พัฒนาระบบ จัดการดำเนินการของแต่ละกรณีเป็น 3 กลุ่ม: **จำเป็น**, **ยอมรับได้**, **ไม่ควรทำ** พร้อมเหตุผล โดยไม่เห็นผลของระบบ แล้วรายงานความสอดคล้องระหว่างผู้ประเมิน (เช่น Cohen's kappa)
2. ทบทวน playbook ในฐานความรู้ให้สอดคล้องกับคำตอบอ้างอิง (เช่น การแยกเครื่องใน PB-POWERSHELL และ PB-C2) และบันทึกเป็นรุ่นใหม่ ไม่แก้ย้อนหลัง
3. ตรึงคำตอบอ้างอิงด้วย hash และ commit **ก่อน** การทดลองใหม่
4. ถือว่า TC-01–TC-10 เป็น **ชุดพัฒนา** และสร้าง **ชุดประเมินใหม่** ที่ไม่ได้ใช้ระหว่างพัฒนา อย่างน้อยสถานการณ์ละหนึ่งกรณีใหม่ และควรเพิ่มกรณีที่ใช้กฎมาตรฐานของ Wazuh มากขึ้น
5. รายงานผลบนคำตอบอ้างอิงเดิม (v3.3) คู่กับรุ่นที่ผู้เชี่ยวชาญตรวจ โดยไม่แทนที่กัน ห้ามเปลี่ยนการดำเนินการเป็น "ยอมรับได้" เพียงเพื่อให้คะแนนสูงขึ้น

ผลเพิ่มที่รายงานได้หลังข้อ 1: นอกจาก strict exact-match แล้ว ให้รายงาน required coverage และสัดส่วนการดำเนินการที่ "ไม่ควรทำ" แยกจากที่ "ยอมรับได้"

### B4. การทำซ้ำและความแปรผัน

- รันทุกกรณีของชุดประเมินซ้ำอย่างน้อย 5 รอบเต็มกระบวนการ (ไม่ใช่แค่สร้างคำแนะนำซ้ำ) กำหนดจำนวนรอบล่วงหน้า และไม่ตัดรอบที่ล้มเหลวออก
- รายงานค่าเฉลี่ยและช่วงความเชื่อมั่น (เช่น Wilson interval สำหรับสัดส่วน, bootstrap สำหรับเวลา) และผลรายรอบ
- ทำซ้ำกับแบบจำลองอย่างน้อย 2 แบบ และบันทึกค่า temperature/seed
- แยกความแปรผันจากฝั่งหลักฐาน (สร้างการโจมตีใหม่) กับฝั่ง LLM (หลักฐานชุดเดิม) ดังที่การทดลอง 15 รอบทำไว้

### B5. การทดสอบความล้มเหลว

เพิ่มกรณีที่ตั้งใจให้ระบบต้องหยุดหรือปฏิเสธ และรายงานพฤติกรรมเมื่อไม่สำเร็จ:

| กรณี | คาดหวัง |
|---|---|
| หลักฐานไม่พอ / IOC อยู่ในฟิลด์ที่ไม่ได้อ่าน | ไม่มีคำแนะนำที่อ้างเป้าหมายนอกหลักฐาน; บันทึกเหตุผล |
| เป้าหมายไม่ตรงชนิด | ตัวตรวจปฏิเสธ |
| การดำเนินการที่นโยบายไม่อนุญาต | ตัวตรวจปฏิเสธ |
| IR ปฏิเสธแล้วเลือกการตอบสนองอื่น | ระบบบันทึกการตอบสนองที่ต่างจากคำแนะนำได้ (ชุดทดสอบปัจจุบันทำไม่ได้) |
| เหตุการณ์ยังเกิดซ้ำหลังการตอบสนองในการทดลองหลัก | ค้นหาซ้ำได้ NOT_RESOLVED และเปิดรอบใหม่ |
| มีเพียง IOC ชื่อผู้ใช้ | หลังปรับปรุง: ค้นหาซ้ำด้วยชื่อผู้ใช้ร่วมกับ agent/rule ได้ |

### B6. การศึกษากับผู้ปฏิบัติงาน (ถ้ามีเวลาและได้รับอนุมัติ)

ให้นักวิเคราะห์ IR จริงตัดสินใจกับคำแนะนำของระบบในสถานการณ์จำลอง วัดเวลาตัดสินใจ อัตราการยอมรับ/ปฏิเสธ และเหตุผล ต้องผ่านการพิจารณาจริยธรรมการวิจัยในมนุษย์ของสถาบันก่อน หากไม่ได้ทำ ให้คงข้อจำกัดว่าไม่ได้วัดภาระงานหรือเวลาของคน

## C. ลำดับงานที่แนะนำ

1. ปิดส่วน A ทั้งหมด → ฉบับนี้ส่งได้ในขอบเขต "ระบบต้นแบบในห้องปฏิบัติการ"
2. ถ้ามีเวลาเพิ่ม: B3 (คำตอบอ้างอิงโดยผู้เชี่ยวชาญ) → B2 (offline เปรียบเทียบ) → B4 → B5 ตามลำดับ เพราะ B2 และ B4 ต้องใช้คำตอบอ้างอิงที่ผ่านการตรวจแล้วจึงจะมีความหมาย
3. เขียนผลและอภิปรายใหม่ก่อน แล้วจึงแก้บทคัดย่อและสรุปเป็นขั้นสุดท้าย
